# 决策记录（Decision Records）

## DR-001 2026-11-18 翻译资产采用 gettext PO 工作流 [状态: 生效]
- 背景: libuv 官方文档（41 个 rst，约 296KB，Sphinx 构建）需翻译为中文并跟随上游持续更新，增量翻译是硬需求；全网调研确认无现成项目/机制可复用（最接近的 neverwin/libuv-docs-chinese 为直译 rst、2019 年停更）。
- 选项与权衡: A(gettext PO + sphinx-intl + msgmerge：增量原生、业界成熟、机器校验完善；代价是仓库内中文不可直接以 rst 阅读、构建多一步); B(直译 rst + 段落哈希清单：中文直接可读；弃用——同步工具自研自维护、rst 段落切分对表格/指令有边界风险); C(rst 转 Markdown + 现代文档站：弃用——丢失 C-domain 交叉引用渲染、每次上游更新伴随转换漂移，diff 噪音大)
- 结论: 采用方案 A，翻译资产为 locale/zh_CN/LC_MESSAGES/*.po，构建 sphinx -D language=zh_CN，发布 GitHub Pages。
- 理由: 增量同步靠 msgmerge 模糊匹配自动化，无需自研 diff 工具；msgfmt -c 可机器校验 rst 标记完整性，适配 agent 批量翻译的质量门禁。
- 影响: 仓库整体结构（§4）、同步脚本设计（§6）、agent 翻译工作流（§5）
- 记录时间 / 会话: 2026-11-18 / libuv-zh-docs 翻译计划会话

## DR-002 2026-11-18 翻译范围定为全量 41 文件、分 5 期发布 [状态: 生效]
- 背景: 上游文档含 guide 入门（12 文件）、核心 API（19）、网络/进程/线程 API（8）、freertos 与索引（2），需确定范围与发布节奏。
- 选项与权衡: 全量分批(完整且每期有可见发布物；弃用理由——无，工作量可由批次控制); 仅 API 手册(弃用——guide/design 缺失则中文站对初学者价值大减); 仅 guide 入门(弃用——API 手册才是跟随上游变更的主体，先翻入门部分会造成后续增量同步与初译混行)

- 理由: 单版本完整中文站才有长期价值；分批保证每期都有可用发布物，且 P0 完成后增量同步机制即就位。
- 影响: 批次规划（§7）、里程碑与发布点

- 背景: P0 需创建远程仓库并上线 GitHub Pages；托管方式影响发布自动化与可见性。
- 选项与权衡: GitHub 公开仓库(Pages 免费自动发布、可被 fork 续维护、符合 CC-BY-4.0 传播精神); GitHub 私有仓库(译文未完成前不对外，弃用——Pages 免费计划不可用，需 Pro 或 gh-pages 分支变通); 暂不建远程(零暴露，弃用——无 CI 自动同步与发布，upstream-watch 无处运行)

- 理由: 全自动发布 + 开源传播 + 零成本；公开即发布的代价已由 CC-BY-4.0 许可与免责声明覆盖。

## DR-004 2026-11-18 初译期锁定基线 v1.53.0，v1.0 后随上游 release 切换 [状态: 生效]
- 背景: 上游约每 2–3 个月发版，初译期（P0–P4）可能撞上 v1.54.0；用户要求"跟随官方持续更新"，需明确初译期的基线策略。
- 选项与权衡: 初译期锁定基线(增量与初译不混行、po 变动最小、批次工作量可预估，弃用理由——更新起点延后至全量完成); 随发随切(始终基于最新版，弃用——初译与增量混行、fuzzy 重译量不可控、工作量不可预估)
- 结论: P0–P4 锁定 v1.53.0；期间上游发版仅由 upstream-watch 自动开 issue 记录，不切基线、不重抽 pot；v1.0 发布后按 §6 流程切换下一 release。
- 理由: 与"跟随官方持续更新"不冲突，只是把切换时点放到翻译资产完整之后，一次性处理增量，质量与排期均可控。
- 影响: §6 增量同步流程、§7 批次发布点、upstream-watch.yml 行为
- 记录时间 / 会话: 2026-11-18 / libuv-zh-docs 计划复审会话

## DR-005 2026-11-19 上游 role 缺冒号笔误条目：修邻接误报 + 译文逐字镜像 [状态: 生效]
- 背景: P3 两处上游笔误（role 缺前导冒号，udp.rst:456 / stream.rst:214）在现有门禁下无三全译法——规范化为真 role 触发 sphinx 引用一致性 warning 超基线；逐字镜像触发 check_markup 邻接误报 error；删残片改写触发 role 对等 error。
- 选项与权衡: A(修邻接误报+镜像笔误，弃用理由——无); B(规范化译文+conf.py 压制 i18n.inconsistent_references，弃用——全局压制会静默未来真告警); C(规范化译文+并入基线，弃用——基线失去上游存量纯度)
- 结论: check_markup.py 邻接 role 正则加 `(?<![\w])` 负向前瞻（「c:func:`…`」残片降级按单反引号判邻接，docutils 中反引号前「:」属合法起始前缀、渲染不损坏）；两条 msgstr 逐字镜像笔误残片，中文页与英文页渲染一致。
- 理由: 唯一全门禁绿、零豁免、不压制未来告警的路径；符合「标记原样保留 + 上游笔误登记报告」既有纪律。
- 影响: scripts/check_markup.py（adjacency_errors）、udp.po / stream.po 各 1 条 msgstr；后续批次同类笔误照此处理
- 记录时间 / 会话: 2026-11-19 / libuv-zh-docs P3 批次会话
